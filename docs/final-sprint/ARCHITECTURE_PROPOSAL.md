# P1 architecture proposal — approved 25 November 2026

25 November 2026. User approved all three increments; implementation is progressing incrementally. This document describes the target design, not a completion claim. Extends the existing modular monolith, Flutter application, PostgreSQL and EF Core. No service split or replacement of functioning modules.

Repository rule: AGENTS.md, Development Workflow: **“Explain significant architectural changes and request user approval before implementing them.”** The changes below introduce persisted aggregates and expand scheduling/privacy boundaries; the P0 hours fix does not require them.

## Increment 1: assigned work execution (#6, #8)

Add tenant-scoped WorkOrder, WorkOrderStage, WorkStageAssignment and WorkOrderEvent tables. A unique (BusinessId, AppointmentId) prevents duplicate conversion of the same booking. Composite tenant FKs and RESTRICT deletion preserve history; xmin guards mutable records. Appointment remains the reservation/lifecycle authority (Confirmed/Cancelled); work order records execution, not a second booking calendar. Existing appointments are not converted or completed automatically.

First deliverable: owner explicitly creates a work order from a confirmed existing single-stage appointment using its agreed price/duration/resource snapshots. Employee lists and detail return only assigned work; owner can read tenant-wide progress. Stage start/complete, assignment changes and work-order creation use one transaction, business-first lock order, revalidated memberships/session, request ID receipts, actor events and optimistic versions. Repeating a completed request returns its stored result; a new request attempting an invalid transition is rejected.

Use Scheduled → Ready → InProgress → Completed, with Paused/Cancelled only through explicit authorized transitions. Stage order is enforced; finishing a stage makes the next stage Ready and the last required completion completes execution. Cancelled booking cannot start. Starting work requires a current authorized assignment, compatible area capacity and no other active stage for any selected employee. Paused stages retain resource occupation until explicitly resumed/reassigned/cancelled; no implicit release. Reassignment is owner-controlled, revalidates replacement staffing and records old/new assignments; employee cannot assign themselves or access management/finance.

Add explicit service-stage templates (ordered sequence, name, active minutes, area, required employee count) in a subsequent focused additive migration. Existing explicit single-stage requirements remain valid. On booking, snapshot ordered stage definitions and employee allocations, derive sequential UTC stage intervals, validate each against hours/full employee coverage/area peak using the same engine and reserve each stage separately. Extend the current active-resource unique indexes to include stage identity; do not drop integrity protection without a replacement. Legacy rows retain existing reservations and semantics. Total active duration comes from configured stage minutes; do not infer stages from Turkish service names.

Execution uses server actual-start/completion timestamps and accumulated paused seconds. Responses include serverNowUtc; Flutter derives remaining/overdue time from authoritative timestamp differences plus a monotonic local elapsed clock. Refresh after foreground/reconnection and navigation. No per-second database writes or automatic completion. Device clock changes must not move authoritative progress. Each action refreshes server data; owner sees overdue and overlap risk with subsequent planned reservations. **Do not move those reservations automatically.**

Verification: domain invalid/duplicate transitions, assigned-only and cross-tenant HTTP denial, two concurrent starts/completions/reassignments, rollback after partial writes, exact resource occupancy, restored countdown/paused/overdue widgets, owner agenda-to-employee-to-completion live demonstration.

## Increment 2: customer booking on the same calendar (#11, #10, #4)

Add paginated published business directory/search/detail with a deliberate safe DTO (business name, intended public address/contact, timezone, opening hours, published services/prices). Never serialize employee identities, private customer data or finances into discovery/slot responses. Return available slot instants and estimates; server chooses eligible allocation rather than exposing employee roster. Preview is advisory; creation revalidates under the existing business lock.

Extend BookingSource with Customer. Add nullable CustomerProfileId/OwnedVehicleId to the existing Appointment and relax LocalCustomerId/LocalVehicleId nullability only with a replacement database check: OwnerPhone must have the original local customer/vehicle pair, while Customer must have the customer profile/owned vehicle pair. Composite ownership foreign keys ensure a selected vehicle belongs to that profile; the API additionally verifies the authenticated user. Existing rows retain all original references. Extend response contracts and Flutter parsing to support both reference types while always displaying immutable name/plate/service snapshots. This avoids duplicate tenant plate collisions and avoids inventing verified links. Never auto-link an existing local person/vehicle by name or plate, or grant the owner access to unrelated customer history. No separate customer calendar/table of competing reservations.

Extract role-neutral locked scheduling allocation from the current owner-only wrapper so both sources share hours, stage sequencing, full availability and capacity validation. Retain fresh role-specific authorization around the engine. Customer lists/detail/cancel/reschedule query the authenticated customer ownership fields on the backend; owner agenda naturally reads the same appointments.

Persist a business booking policy with CancellationRescheduleCutoffMinutes=120 initially; later owner configurability must not require changing the scheduling engine. Automatically confirm when all server capacity checks pass. Allow customer cancel/reschedule when serverNowUtc <= originalStartUtc minus cutoff; after that reject. Rescheduling cutoff uses the current original appointment start and revalidates proposed resources, preserves original on failure, and checks the new start is not in the past. Owner explicit changes retain their current separate authorization. Store policy/snapshot evidence for audit. Cancellation releases reservations exactly once. Never move appointments after execution overrun.

Verification: own-vehicle authorization, cross-customer/tenant privacy, directory data disclosure, 2-hour equality and one-tick-late cutoff, different timezone/local date, customer-vs-owner last-slot race, repeated create/cancel requests, unchanged original booking after failed reschedule, actual Flutter customer booking appearing in owner agenda.

## Increment 3: owner finance (#7)

Add tenant-scoped Payment, ManualIncome, Expense and configurable PaymentMethod records. Store explicit currency (initial TRY) and decimal amounts; positive values and same-tenant foreign keys enforced in database and backend. Initial methods: cash, card, bank transfer. No payment gateway. Category/description/date/supporting reference and optional employee membership belong to the tenant; no employee access to financial APIs.

Completed work-order snapshot total is earned service revenue. Payment ledger is cash collected and never added again to revenue. Manual income is separately classified. Allow positive partial payments up to the remaining collectible balance, with business locking/idempotency preventing concurrent overpayment. Corrections use explicit audited reversal/correction entries; do not silently edit historical totals. Refund workflow and taxes are outside this increment unless separately defined.

Dashboard labels distinguish earned revenue, collected payments, unpaid balance, recorded expenses and cash operating balance. Date ranges use business-local dates converted to UTC boundaries, half-open periods and decimal aggregation. Service revenue derives from completed service snapshots; payment-method breakdown from payment records; expense breakdown from expenses. Do not label cash balance as accounting net profit. Daily/weekly/monthly trends are useful presentation scope; employee rankings and advanced analytics wait.

Verification: sum/rounding/currency, partial/concurrent payments, duplicate request, no double counting, date/timezone boundaries, owner/employee/tenant access, chart fixtures vs actual API totals, completed wash → payment + expense → dashboard live demonstration.

## Migration and delivery safety

Each increment uses a separate reviewed additive migration and focused branch/PR. Preserve seven existing migrations and demo data; inspect generated SQL and verify upgrade from current schema on a disposable database before any explicitly authorized demo migration. Adding new statuses/sources must update current enum/check constraints and immutable snapshot/history triggers deliberately. Backfill only documented deterministic legacy metadata; no invented work completion/payment records. New read models must handle legacy appointments without work orders/customer ownership fields.

No push/merge or database deployment is implied by approving this design. Tests, mobile integration and reviewable changes must precede each delivery. Keep existing issues open until their whole acceptance criteria pass. Kanban updates remain pending until Projects write access exists.
